## 1. Decisions taken

- **E2E writes to a local Postgres**, not Neon. The `acme` bottle store is a live
  client-demo tenant; a suite that rings up test sales must not touch it.
  *(Docker was the first plan; see §0. It is a native PostgreSQL 16 on the same
  port `DATABASE_URL_TEST` already named, so nothing else changed.)*
- **Two databases on it, not one.** `huchu_test` for vitest, `huchu_e2e` for
  Playwright. The unit suite creates and drops tenants on every run; sharing one
  database would have `pnpm test` quietly delete the shop the e2e suite sells
  from.
- **Strict host routing throughout, via preview host nomination.** *(Revised
  2026-09-01 — this originally said "one elevated hosts-file script". We cannot
  add hosts entries on this machine: no admin rights, and no wildcard escape
  since the router's DNS-rebind protection hijacks `*.localtest.me`.)*

  `docs/_start-here/STAGING_PREVIEW.md` documents the facility the app already
  has for exactly this: a non-production deployment can be *told* which host to
  behave as, via `?__tenant=`, `?__host=`, the `x-huchu-preview-host` header, or
  the `__huchu_preview_host` cookie. One origin therefore reaches all five
  tenants and all four portals.

  This is not weaker than hosts entries — it is the same enforcement. Sign-in is
  still scoped to the tenant the nominated host resolves to, the session still
  carries that tenant's `allowedHosts`, enforcement still runs against the
  nominated host, and an inactive tenant is still refused. Only the hostname
  arrives by a different route. The origin is deliberately not `localhost`,
  because `lib/platform/preview-host.ts` relaxes strict enforcement for loopback.
- **Every vertical gets its own tenant slug.** One tenant cannot credibly be a
  bottle store and a school.
- **Screenshots are a first-class output**, not a by-product — see §6.

### 2a. Why 0.7 and 0.8 are in scope

They started as an adjacent risk and are now part of the plan. Two reasons:

- **0.7 is a correctness precondition.** If vitest can still reach Neon, so can a
  mis-set `.env` during the fix loop — and the fix loop is dozens of runs long.
  The guard has to exist before we start, not after.
- **0.8 is a screenshot precondition.** Anything shot against Neon has 390
  `Test Company` and `Timetable Test 1786…` rows in reach of a tenant switcher,
  a global search or an admin list. Marketing screenshots cannot have that in
  frame.

**The existing script only covers a fifth of the problem.** Read on 2026-09-01:
`clean-provision-test-tenants.ts` matches `/^provision-[a-z]+-\d+-\d+$/` and
nothing else — deliberately narrow, because "a prefix match alone would be one
badly-named real tenant away from deleting a shop". That is ~20 of the ~390
rows. It also unwinds a *retail* relation graph specifically (price entries,
price list, stock, locations, products, registers, site, accounting), because
`Site` is `onDelete: Restrict`.

So 0.8 is not "run the script". It is:

1. Extend the matcher to the other generated shapes, each as a **precise regex**,
   not a prefix: `test-co-<hex>`, `timetable-test-<digits>`, `payslip-<digits>`,
   `settlements-<digits>`, `portal-identity-<digits>`, `audit-school-<digits>`,
   `zreport-fixture-<digits>-<digits>`, `bottle-store-<digits>-legacy`.
2. Generalise the teardown — school, payroll and settlement fixtures have
   different relation graphs from retail, and each will hit its own `Restrict`.
3. Report-only, review the list by eye against the named demo tenants, then apply.

The deletion is the one destructive step in this plan. It never targets a named
demo tenant, and the script already refuses outright if `DATABASE_URL` looks like
production.

### 3a. Three harness bugs worth remembering

All three were mine, all three surfaced on the first run, and each is now
encoded in the harness rather than in somebody's memory.

- **The nomination header broke the page it was photographing.** Playwright's
  `extraHTTPHeaders` applies to *every* request the context makes, cross-origin
  included, and a custom header on a cross-origin request triggers a CORS
  preflight. Google Fonts failed with *"Request header field
  x-huchu-preview-host is not allowed by Access-Control-Allow-Headers"*. Hence
  the cookie, which is origin-scoped by construction. `STAGING_PREVIEW.md` names
  the header as the one for the e2e suite; that is right for curl and wrong
  inside a browser.
- **`NEXTAUTH_URL` made every sign-in cross-origin.** Pointed at the central
  host, the post-login RSC fetch was blocked, surfacing as `net::ERR_ABORTED`.
  It now names the origin the suite browses.
- **`page.goto` rejects when the app navigates first.** `ERR_ABORTED` on
  `/payroll/runs` — and the failure screenshot showed the payroll sidebar fully
  rendered behind it. The page had arrived; only the bookkeeping disagreed.
  `visit()` retries and then checks where it actually landed, so a genuine
  redirect still fails, and says so in those words.

**Exit gate:** `e2e/smoke-tenants.spec.ts` green. **Met.** The existing 31 specs
still build per-host URLs of their own and have not been retro-fitted — Phase 3.1.

### 4b. Three things the seeds had to work around

- **Prisma refuses `null` in a compound-unique `where`.** `SchoolClassSubject`
  and `SchoolAttendanceSession` are both unique on a tuple including the
  nullable `streamId`, and these classes have no streams, so `null` is the
  normal case. `upsert` fails with *"Argument `streamId` must not be null"*;
  both are now `findFirst`-then-write.
- **`provisionSchool` builds a fee structure for Term 1 only**, and returns
  early if any structure exists. A school opened in January and now teaching
  Term 3 therefore has nothing to invoice against, and the whole fees module
  renders empty. `seed-school-demo.ts` builds one per class for the current term.
- **`GoldDispatch.handedOverBy` is an Employee, not a User** — the person who
  physically handed the bar over at the gate, where `GoldPour.createdBy` is the
  User who keyed it in. Passing a user id is a foreign-key violation, and was.

## 10. Found on the way: the migration history could not rebuild the schema

Found 2026-09-01 during step 0.2. **Fixed the same day**, with a regression
guard. Kept here because the failure mode is worth remembering.

`npx prisma migrate deploy` against an empty database applies 59 migrations and
then fails:

```text
Migration name: 20260819090000_scope_trim_drop_dropped_module_schema
Database error code: 42703
ERROR: column "sourceType" does not exist
```

The chain:

1. `StockMovement.sourceType` was added **by script, not by migration** (S-2) —
   one of the several changes that shipped that way because `prisma db push`
   could not reach the pooled development host.
2. Migration `20260819090000` *references* that column. It was written when the
   live database already had it, so it worked.
3. The column is only ever **created** by `20260820130000_script_applied_schema_catchup`.
4. `…0819…` sorts before `…0820…`. On a fresh database the reference runs before
   the creation.

Existing databases are fine, and always were — the script had already added the
column out of band. Only a from-scratch build fails, which is why nobody hit it.

**Why the verification missed it.** The catch-up migration's header says it was
"generated with `prisma migrate diff --from-migrations --to-schema` against a
scratch shadow database, then verified by re-running the same diff with this
file in place — the result is empty". That compares *end states*. It cannot
detect a step that will not execute in order. The header also asserts that
"every database created from migrations afterwards executes it for real", which
is the claim this disproves.

**Why it matters beyond this suite.** `prisma/migrations` is the stated source of
truth and what production applies. A history that cannot rebuild is a
disaster-recovery gap, and it blocks any from-scratch environment: a new
developer, CI, a restore.

### What was done

**1. `20260819090000` guards both its references.** It touched the column twice —
a `SELECT count(*)` inside the `DO $$` guard block, and the `ALTER COLUMN … TYPE`
that converts it to the rebuilt enum. Both are now behind an
`information_schema.columns` existence check.

The count had to become `EXECUTE`'d dynamic SQL. PL/pgSQL plans a static
statement when the block runs, so a plain `SELECT` against a missing column
raises 42703 whether or not an `IF` wraps it — the guard only means something if
the statement is not planned until it is reached.

Nothing is lost by skipping either on a fresh database: the catch-up creates the
column a step later, and by then `AccountingSourceType` is already the rebuilt
enum, so the column is created correct rather than created wrong and converted.
Verified on a from-scratch build: `sourceType` is `AccountingSourceType`,
nullable; `AccountingSourceType_old` is gone; zero `SCRAP_*` labels remain.

**2. The false claim in the catch-up's header is corrected in place**, since that
header is what a future reader would trust.

**3. `pnpm verify:migrations` now exists** — `scripts/verify-migrations-from-scratch.mjs`.
It builds a throwaway database, runs `migrate deploy` (proving every migration
**executes, in order**) and then diffs the result against `schema.prisma`
(the end-state check, kept). 14.7s, so it belongs in CI.

Proved it catches the original bug: with the pre-fix migration restored it exits
1 on `column "sourceType" does not exist`. A guard nobody has seen fail is not a
guard.

### The checksum question, answered

Editing an applied migration changes its SHA-256, which Prisma records in
`_prisma_migrations`. Measured against Prisma 7.2.0 by rewinding a built
database's checksum to the pre-edit value:

| Command | Effect |
|---|---|
| `prisma migrate deploy` | **Unaffected** — "No pending migrations to apply." Applies pending migrations only; does not re-verify applied ones. |
| `prisma migrate status` | **Unaffected** — "Database schema is up to date!" |
| `prisma migrate dev` | **Refuses**: "The migration … was modified after it was applied. We need to reset the schema." |

So production and staging need nothing at all. Developer databases need one
re-stamp, or the next `migrate dev` offers to drop the database — which on the
shared development database would be a catastrophe dressed as a prompt:

```bash
DATABASE_URL=<your dev database> node scripts/restamp-migration-checksums.mjs          # report
DATABASE_URL=<your dev database> node scripts/restamp-migration-checksums.mjs --apply
```

Two migrations need re-stamping: `20260819090000` (the fix) and `20260820130000`
(the header correction). Neither edit changes what the migration does on a
database that has already applied it, which is the condition that makes
re-stamping legitimate rather than a cover-up.
