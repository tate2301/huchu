# Corelith Campus — conduct, exams, leavers

Fourteen screens, designed and specified, none of them built. This folder is what an
engineer needs to build them without the conversation that produced them.

The wider expansion drew twenty-six screens across five areas. Three areas were kept:

| Page | Screens | Stories | Spec |
|---|---|---|---|
| Conduct and pastoral | 5 | S-12.1 – S-12.3 | [conduct.md](conduct.md) |
| Public exams | 5 | S-13.1, S-13.2 | [exams.md](exams.md) |
| Leavers and alumni | 4 | S-13.4, S-13.5 | [leavers.md](leavers.md) |

Group and campuses (S-11.x) and campus operations (S-14.x) were drawn and set aside. Their
artboards and sources are still in `design/campus/` if they are wanted later.

## The four artefacts per screen

Every screen ships four things, and each answers a different question.

| Artefact | Answers |
|---|---|
| `design/campus/expansion/<Screen>.dc.html` | What does it look like? |
| `design/campus/checklist/<Screen>.json` | What exactly does it say? **This is the contract.** |
| `design/campus/spec/<Screen>.html` | The rendered page content, as a fragment |
| The page spec in this folder | What does it **do**, and what has to exist first |

The checklist is generated by the primitives that draw the screen — every table column, card
title, section heading, stat, filter, band chip and button files itself as a side effect of
being drawn. It cannot drift from the artboard. **Match its copy verbatim.**

Read, in this order:

2. [`../13-campus-expansion-canvas.md`](../13-campus-expansion-canvas.md) — the shell (one
   sidebar, not two) and the six composition rules these screens are drawn to.
3. [`../10-campus-screen-contract.md`](../10-campus-screen-contract.md) — how a campus screen
   is actually built in this repo: file layout, primitives, query conventions, the DoD.
4. [`../11-campus-states-and-motion.md`](../11-campus-states-and-motion.md) — the eight

5. [`foundation.md`](foundation.md) — the expansion's own law sheet, if you want the
   reasoning behind the shell and the composition rules.

Then the page spec for whatever you are building.

## None of this exists in the database yet

This is the part worth reading before planning a sprint. Verified against
`prisma/schema.prisma`:

- **No `SchoolIncident`, `SchoolMerit`, `SchoolDetention` or `SchoolPastoralNote`.** The
  whole conduct page is new tables. `DisciplinaryAction` exists but is an HR model for
  employees, not pupils.
- **No `SchoolExamSeries`, `SchoolCandidate` or `SchoolExamEntry`.** `SchoolAssessmentKind`
  has an `EXAM` member, but it is an internal assessment type, not a public exam.
- **No `SchoolLeaver` and nothing alumni-shaped.** `SchoolStudent` carries a status, and
  `applyYearRollUp` already graduates a pupil — graduating just leads nowhere afterwards.
- **No campus column anywhere.** `campusId` appears zero times across all 66 `School*`
  models. That is the S-11.x work, which was set aside.

Each page spec has a **"Before any of this can be built"** section enumerating exactly what
its screens need.

## Where these sit in the product

They add four sidebar rows and one group:

| Group | Rows |
|---|---|
| **Conduct** (new, after Classroom) | Behaviour log · Merits and demerits · Detention |
| **Welfare** | Pastoral notes joins Bed board and Health and welfare |
| **Results** | Exam series joins the four internal-results rows |
| **Students** | Leavers and Alumni join the roll |

Pastoral notes sits under **Welfare**, not Conduct, on purpose. A pastoral note is not a
discipline record, and filing it under Conduct would tell everyone who opened the menu that
it was.

## Tracking what is built

```bash
node scripts/campus-conformance.mjs
```

All fourteen report under **"NO PAGE — the canvas draws it, nothing renders it."** That is
the correct status for a design nobody has built, and that list is the build queue. Building
the route is what removes the row; nothing needs updating by hand.

Once a route exists, the screen moves into the coverage table and the report starts telling
you which of its strings are missing from your implementation.

## Regenerating the artboards

```bash
node design/campus/build-expansion.mjs
```

Edit `design/campus/screens/<page>.mjs` and rerun. That rewrites the artboards, the rendered
specs and the checklists together, so the contract can never fall behind the drawing.
